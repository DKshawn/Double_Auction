# 单市场并发优化（2026-10-28）

保留逐笔 CDA 撮合、价格时间优先、数据库提交后确认成功，以及“提交报价”和“接受最优订单”的独立操作日志。

本次落实三项调整：

1. 同市场操作使用已生成的事件、期次变化和请求凭据判断是否需要保存，减少锁内整份状态的反复 JSON 比较。将市场状态、归档订单、请求凭据、审计事件和通知合并为一条 SQL，仍在同一个事务中提交或回滚；没有把多名学生的命令合并成一个事务。
2. 新的学生请求凭据写入 `auction_market_receipts`，以房间、市场、学生及请求 ID 唯一定位。市场行中的 `receipt_count` 记录新增凭据数量。已有 `receipts` JSON 保留原样、不回填；处理命令时同时兼容旧 JSON，并在取得市场锁后的新 SQL 快照中查询当前请求，防止两个进程同时重试时重复执行。教师导出仍能读取全部凭据。
3. 同一市场每轮广播都保留 40 ms 的合并窗口，持续繁忙时也合并更新。调用者的成功响应仍等待交易提交；其他订阅者的画面更新会增加少量合并等待。

新增表和列是附加结构，历史房间状态、价格、成交、事件、时间及旧请求凭据没有批量改写。旧结构兼容测试确认，添加结构前后的历史 JSON 与房间更新时间一致。部署后需使用一致版本的写入服务；旧代码不会读取新凭据表。本次没有部署或连接线上数据库。

本地对照使用相同的双应用进程、独立 PostgreSQL、192 名学生、1 名教师和 12 个负载工作线程。主要阶段维持 193 路 SSE，同一市场不分组。响应时间为从发起请求到收完 JSON 的 P95。

| 场景 | 优化前 | 优化后 | 降低 |
| --- | ---: | ---: | ---: |
| 32 人集中报价 | 0.405 秒 | 0.239 秒 | 40.9% |
| 96 人集中报价 | 1.476 秒 | 0.983 秒 | 33.4% |
| 192 人集中报价 | 5.164 秒 | 2.515 秒 | 51.3% |
| 192 人持续尝试改价 | 6.424 秒 | 3.232 秒 | 49.7% |
| 96 人同时提交可成交报价 | 4.956 秒 | 1.867 秒 | 62.3% |

192 人集中报价的三波共 576 个请求，优化前后数量相同；广播批次从 933 降到 247。持续改价使用固定 16 秒的发起窗口，随后等待在途请求完成，每位学生上一请求尚未完成时不发下一请求。最终完成请求从 613 增至 1,040，因此持续改价一行不是完全相同的已发送请求量对照。后续成交阶段的历史数量也会受此影响。

普通单笔报价 P95 从 23.1 ms 变为 24.0 ms，未观察到低负载响应改善。高峰仍有约 2–3 秒等待，不能视为已经消除同一市场的串行瓶颈，也不能直接推断 Vercel/Neon 的线上响应。

优化后压测共 2,303 个请求均与服务器操作日志按请求 ID 对齐。118 笔成交与事件账一致，无重复成交或单位超卖；96 人接受同一笔最优订单时，只有 1 人成功，另 95 人按规则被拒绝。2,208 条成功操作与 2,208 条新增请求凭据及计数器一致，旧 JSON 凭据长度保持为零。

验证包括后端回归、真实 PostgreSQL 独立连接并发重试、写入后异常回滚、旧格式兼容、操作日志、页面刷新后上传、丢响应重试，以及 SSE 换连接和暂停恢复。原始结果保存在 `work/local-optimization-192-20261028/`；对照基线在 `work/local-latency-192-20261028-6b47a2c1/`。
